# 离线库存

## Syndicator 存档

- 离线库存只读取所选游戏版本各账号的 `WTF/Account/<账号>/SavedVariables/Syndicator.lua`，从 `SYNDICATOR_DATA` 还原角色装备、随身背包、个人银行和公会银行。各账号的快照独立展示。
- 选择 Syndicator 是因为它在同一个账号级存档中提供这四类数据，并保存可用的物品链接、格位、数量、部分绑定状态和品质。客户端归档负责补充本地物品定义与图像。两者分别描述角色或容器中的物品实例，以及这个版本的物品定义。
- 保留物品的原始格位、空格和容器。角色背包与个人银行按版本解释容器类型，个人银行支持分页记录。战团银行、邮件和拍卖是其他数据范围。
- 背包、个人银行和公会银行使用固定大小的方格。物品名称在提示中显示，堆叠数量标在图标右下角。公会银行保留按列排列的七行格位。
- 物品链接中的字段用于解析基础物品 ID、附魔 ID 和按格位排列的宝石 ID。装备计算保留宝石字段中的空位置，以免把后面的宝石挪到前一个插槽。Syndicator 的 `isBound` 表示快照中物品的实际绑定状态。库存提示和物品详情显示 DB2 的 `Bonding` 规则，无绑定规则时省略该行。
- 监听 SavedVariables 目录中的源文件变化，兼容游戏替换文件的写入方式。读取到尚未写完的 Lua 时重试。一个账号有解析错误时，页面在可用的情况下保留其上一份快照，其余账号继续读取。

解析入口在 [inventory.ts](../src/profiles/syndicator/inventory.ts)，页面与监听入口在 [Inventory.vue](../src/pages/Inventory.vue) 和 [useInventory.ts](../src/composables/useInventory.ts)。同步引擎见 [WTFSync 技术方案](technical-design.md)。

### 公会银行的归属与权限

Syndicator 将公会银行写入账号级 SavedVariables 的 `SYNDICATOR_DATA.Guilds[guildKey]`。公会键是公会名加服务器，启用地区唯一名称时可使用规则组名称。该结构已与 Syndicator 293 的 `Tracking/GuildCache.lua` 及实际存档核对。

同一账号的多个角色访问同一个公会时更新同一份记录。公会银行打开后按当前角色的权限查询分页，覆盖保存的 `isViewable`，并在扫描时清空不可见分页的格位。权限较低的角色后来访问，有可能覆盖此前可见的分页。不同账号的公会快照仍各自独立。

公会保存 `bank`、`money` 和 `details`，分页保存 `name`、`iconTexture`、`isViewable` 和 `slots`。`visited` 标记只表示访问过。存档没有访问角色、公会或分页级时间戳。页面的「存档更新于」是整个 Lua 文件的修改时间，权限提示描述的是存档中记录的可见性。

## 本地客户端资料

Windows Tauri 命令 `inventory_catalog` 校验游戏目录的文件系统授权，把请求通过标准输入发给同应用一起构建的 Go 辅助程序。辅助程序从 `.flavor.info` 识别游戏产品，从 `.build.info` 确定构建，再打开该产品的本地 CASC 存储。对于简中物品文本，会读取本地 `Cache/ADB/zhCN/DBCache.bin`，并在热修构建号与客户端相符时应用热修。读取链路使用本机客户端数据。

| 部件                | 接入方式                                                        |
| ------------------- | --------------------------------------------------------------- |
| CASC                | 固定版本的 CascLib Git 子模块，通过 CMake 编译 DLL              |
| DB2 表定义与文件 ID | 将用到的 WoWDBDefs 定义与清单嵌入辅助程序，未知布局按需更新定义 |
| DB2 与热修解析      | WoWSims Forever `v1.0.3` 的 `db2tool` Go 模块                   |
| BLP 解码            | Rust `wow-blp` `0.7.0`                                          |

本项目维护读取流程和请求协议，上游解析器通过固定的子模块或模块版本接入。Go 辅助程序直接读取所需的 DB2 记录。MSIX 同时打包辅助程序、CascLib DLL 和许可证。 [上游来源与许可证](../tools/clientdata/THIRD-PARTY.md) · [Windows 打包说明](../packaging/windows/README.md)

### DB2 布局与定义更新

读取器按当前客户端的 CASC 索引打开 DB2，核对表名对应的表哈希和 WDC5 表头里的布局哈希。若构建号已登记且布局一致，使用对应定义。否则在同名表的定义中按布局哈希匹配。游戏只更新数据时，内置定义可以继续离线使用。解码和简中热修仍使用当前构建号。

内置定义里找不到布局时，先查 WTFSync 应用缓存目录下的 `dbd`，仍未命中才从 WoWDBDefs 的 GitHub 仓库请求同名 `.dbd` 文件。请求只包含公开表名。下载文件通过定义校验、布局匹配和实际解码后才保存，每张表保留一份，单个文件上限 256 KiB。一次辅助程序调用共用 5 秒的下载时限。上游尚未提供对应布局或网络不可用时，受影响的物品资料仍按原有逻辑回退到 Syndicator。游戏数据、热修、CASC 索引和图像继续从本机读取。 [定义选择与缓存](../tools/clientdata/schema_windows.go) · [WoWDBDefs](https://github.com/wowdev/WoWDBDefs)

### 物品字段

DB2 查询包括基础装等、属性、护甲、耐久上限、装备效果、套装门槛、插槽和宝石条件。附魔效果行来自 `SpellItemEnchantment`，原始名称和描述通过实际施加该附魔的法术关联到 `SpellName` 和 `Spell`。套装、附魔及装备效果还依赖相关的法术效果、时长和部分描述中的法术引用。客户端数据或同构建热修缺失时，页面仍可使用 Syndicator 已保存的资料，并标记客户端资料可能不完整。 [Go 读取器](../tools/clientdata/main_windows.go) · [Tauri 命令及解码](../src-tauri/src/clientdata.rs)

`SpellItemEnchantment.Name_lang` 中的 `$k1` 至 `$k3` 对应各效果槽位。固定数值从同版本的 `EffectPointsMin` 填入，适用于附魔、宝石和镶孔奖励。遇到缺少数值或依赖缩放的占位符时，界面省略未解析的效果行并尽量显示名称。泰坦重铸的附魔 `3754` 对应法术 `24162`「愤怒预言」，其效果值为 58 攻击强度和 24 爆击等级。 [效果文字解析](../src/lib/item-catalog.ts)

消耗品的「使用」说明来自 `ItemEffect` 关联的同版本法术描述。解析器用法术效果及持续时间填入固定数值、周期总量和简单乘除公式。物品本身的描述来自 `ItemSparse.Description_lang`，按客户端换行标记显示。说明中的数值无法从本地资料解析时，省略未解析的法术说明。 [物品说明解析](../src/lib/item-catalog.ts)

物品的直接图标 ID 为空时，读取器会查同一构建的默认外观和 `ItemAppearance.DefaultIconFileDataID`。无限服的护甲、属性和武器伤害可以来自按装等、品质和部位查表的预算值。只有物品记录缺少直接数值时才计算这些字段。鳍鳞之履使用默认外观的图标 `132535`，实测还原出 79 点护甲和 1 点力量。 [外观与无限服物品数值](../tools/clientdata/item_details_windows.go)

## 装备提示与插槽

- 角色装备页参考国服英雄榜，使用左右装备列和底部武器区，显示物品装等和已穿装备平均装等。左栏宝石排在附魔右侧，右栏相反。武器栏居中且限制列宽，附魔与宝石在武器图标上方横排。装备栏跟随应用主题。深色主题采用英雄榜的史诗紫、稀有蓝和附魔亮绿，浅色主题采用同色系的深色文字。物品、宝石和附魔有各自的提示，装备提示保留装等和套装门槛。
- 空栏位的部位底图通过现有的图标读取和缓存获取，纹理来自游戏客户端的 `Interface/PaperDoll/UI-PaperDoll-Slot-*.blp`。客户端缺少纹理时使用内置占位图。悬停或键盘聚焦时按存档状态显示部位与空栏位或未记录提示。
- 装备详情可通过装备图标或名称触发。宝石和附魔各自触发对应提示，栏位内的空白处不触发。武器详情以整个武器栏位定位，避免弹层遮住正悬停的图标。
- 通过本地客户端的 UI 纹理图集裁出插槽边框。边框体现装备原生插槽颜色，宝石图标使用正常亮度。颜色匹配时用 CSS 火花动画表现，当前每条边 2.5 秒，完整一圈 10 秒，并支持减少动态效果的偏好。多彩槽的匹配动画同时要求多彩条件已满足。
- 装备原生插槽由 DB2 提供。链接中超出原生插槽的已镶嵌位置按额外棱彩槽处理，判断与装备部位无关。额外槽不计入装备自身的镶孔奖励，槽里的宝石仍参加全身多彩条件的计算。原始链接无法判断额外槽由腰带扣、专业或其他来源添加，也无法可靠复原空的额外槽。
- 镶孔奖励未激活时显示灰色。图标和边框来自本地客户端，动画用 CSS 实现。掉落来源、游戏内打开镶嵌界面的操作提示和角色装备配置方案均未接入。角色幻化与当前耐久没有进入这条读取链路。
- 账单使用独立的数据源。账单物品提示的约定是按刚掉落的语境解释拾取后绑定、装备后绑定等规则，缺少物品链接时只展示名字。

## 账号和角色选择

本机设置中的 `inventorySelections` 按规范化的游戏目录保存上次选择的账号，并为各账号保存上次选择的角色。游戏版本目录属于键的一部分。暂时读不到保存的账号或角色时，界面选取可用项，保留用户原来的选择。用户主动选择时才更新设置。 [选择逻辑](../src/composables/useInventorySelection.ts) · [设置 schema 与持久化](../src/composables/useSettings.ts)

## 进程内缓存

三类缓存分别按条目与估算体积设上限，达到任一上限时先淘汰最久未使用的条目。预算衡量保留的数据，包含编码和键的估算开销。页面正在显示的资料、进行中的请求和解析器临时内存属于各自的运行开销。

| 缓存           | 查找键与保存内容                                                                       |                  上限 |
| -------------- | -------------------------------------------------------------------------------------- | --------------------: |
| Syndicator     | 游戏版本目录、账号、服务器、角色与原始角色键。公会用原始公会键。另存账号索引以重组列表 |      32 MiB，8,192 条 |
| 客户端物品资料 | 安装目录、客户端文件签名、记录类型和 ID。物品与实际应用的附魔各用自己的 ID 空间        |     32 MiB，16,384 条 |
| 图像           | 用客户端文件签名、图像类型和 ID 查找。相同的编码图像共用一份内容                       | 64 MiB，16,384 个索引 |

Syndicator 缓存命中时核对文件大小和修改时间，避免重新读 Lua。监听事件会让对应账号失效。账号仍是写盘和重新解析的单位，因为角色与公会记录都在同一个 Lua 文件里。读取前后的存档信息一致时才缓存，避免把一次保存过程中读到的内容当成稳定快照。 [Syndicator 缓存](../src/profiles/syndicator/load.ts)

客户端文件签名来自 `.flavor.info`、`.build.info`、简中热修文件和 `Data/data` 的文件系统信息。命中一部分物品时只查询缺少的物品或附魔。批量读取结果拆成按 ID 保存的记录，包含其套装、宝石条件、附魔、法术效果和时长等依赖。显示时合并当前需要的记录。若读取途中客户端文件签名发生改变，会在未带旧图像的情况下重新读取。缺少资料或图像的结果只短期保留 30 秒，便于客户端补全后重试。 [查询、组装与失效](../src/composables/useItemCatalog.ts) · [按 ID 拆分物品资料](../src/lib/item-catalog-data.ts)

点「重新读取」会跳过所选游戏版本的缓存。缓存保留在应用进程内，退出应用后清空。账号与角色选择保存在设置中，可以跨应用重启恢复。

### 图像请求与编码

图标的查找键包含版本和 `IconFileDataID`，插槽框采用独立 ID 空间。两个版本或两个 ID 的编码内容完全相同时，共用一份图像数据。共享池以完整的 Base64 数据 URL 匹配内容。最后一个索引被淘汰时，释放对应的图像预算。 [图像缓存](../src/lib/item-catalog-cache.ts)

前端将当前客户端已有的图标 ID 和插槽框 ID 传给读取器，对应请求字段是 `known_icons` 和 `known_socket_frames`。读取器先从物品记录取得图标 ID，在打开 CASC 图像前略过已知 ID。这同时省去 BLP 读取、转码和传输。只缺普通图标时可以用 `icon_ids` 单独补图，跳过物品 DB2 查询。插槽框仍需要查找 UI 图集的裁剪信息。请求的所有资料和图像都命中时，直接在前端组装结果。

不透明的物品图标转为 JPEG，质量参数为 80。带透明像素的物品图标和插槽边框保留 PNG，以保留透明通道。这些图像共用 64 MiB 预算。 [请求协议和转码](../src-tauri/src/clientdata.rs) · [图像提取](../tools/clientdata/main_windows.go)

图标的本地编码副本缺失时，读取器用当前构建声明的内容键在同一安装目录的其他本地构建中查找，并校验解码后的哈希。木槌棒的图标 `133053` 在泰坦重铸和正式服的内容键相同，编码键不同，可以通过这条路径补读。 [CASC 读取](../tools/clientdata/casc_windows.go)

如果本地只剩 TVFS 清单，CascLib 仍可能打开存储，但无法按 FileDataID 定位物品表和图标。熊猫人之谜 `5.5.4.71089` 的一次验证中，物品表、附魔表、图标和简中热修都在本机，传统 `ROOT` 清单的编码键缺失。用同构建官方 `ROOT` 校验并解析内容键后，独立验证可从本机读回截图角色的 16 件装备。应用当前的本地读取路径仍依赖已存在的 FileDataID 映射。

### FileDataID 跨版本行为

FileDataID 表示 CASC 中的资源标识，具体文件内容由该构建的根清单映射到内容哈希（CKey）。同一个 ID 及文件名哈希可以保留，图像内容仍可随构建更新。跨版本的资源身份与像素内容需要分别判断。 [TACTSharp 根清单读取实现](https://github.com/wowdev/TACTSharp/blob/main/TACTSharp/RootInstance.cs) · [wowdev 图标文件名列表](https://github.com/wowdev/wow-listfile/blob/master/parts/interface.csv)

对比泰坦重铸 `3.80.2.70522` 与正式服 `12.1.5.70961` 本地简中根清单，从有名称的图标中找到 6,463 个共有 ID，其中 138 个在两边的内容哈希不同。文件内容哈希可能因编码差异变化，因此又提取了实际图标并比较 64×64 主图的 RGBA 像素。

| FileDataID | 图标文件                      |    不同像素数 |
| ---------- | ----------------------------- | ------------: |
| `133079`   | `inv_helmet_100.blp`          | 3,553 / 4,096 |
| `133302`   | `inv_jewelry_necklace_15.blp` | 1,199 / 4,096 |
| `134400`   | `inv_misc_questionmark.blp`   |     0 / 4,096 |

三项的文件名哈希在两个版本中相同。仅凭 FileDataID 跨版本复用图像会把不同构建的图像混用。当前按客户端签名查找，再按编码内容共享，能保留同一资源在不同构建中的图像差异。

## 验证入口

- 前端测试覆盖账号与角色恢复、同名角色按服务器隔离、存档缓存命中与失效、图像共享及淘汰、热修失效、跨查询只补缺少的物品，以及套装、宝石和附魔重新组装后的提示一致性。
- 在 Windows 的 `tools/clientdata/` 执行 `go test -mod=readonly ./...` 可核对已知布局离线读取、未知布局按需获取、定义缓存命中，以及拒绝不匹配或过大的定义。
- 在 `src-tauri/` 执行 `cargo test --locked` 可核对转码行为。不透明图标输出 JPEG，透明图标输出 PNG 并保留 alpha。
- 验证本地辅助程序协议时，先查询有图标的物品，再通过 `known_icons` 带上第一次返回的图标 ID 重复查询。两次的物品表应相同，第二次的图标表应为空。将 `items` 和 `enchants` 留空，并在 `icon_ids` 中传入一个存在的图标 ID 时，应得到一张图和空物品表。泰坦重铸和正式服均可用于此验证。
